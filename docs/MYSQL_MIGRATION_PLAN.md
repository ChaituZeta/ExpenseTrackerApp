# FinTrack — Supabase to MySQL Migration Plan

This document details the architecture, schema conversion mapping, authentication replacement strategy, and execution steps to migrate the backend datastore from **Supabase (PostgreSQL)** to a dedicated **Remote MySQL Server**.

---

## 1. Schema Mapping Reference

Modern MySQL (8.x+) supports JSON types and foreign keys matching PostgreSQL models. The tables map as follows:

| Postgres Entity (Supabase) | MySQL Entity | Mapping Notes |
| :--- | :--- | :--- |
| `UUID` | `VARCHAR(36)` | Standard character-locked UUID strings. |
| `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `BIGINT AUTO_INCREMENT` | Traditional auto-increment key sequences. |
| `TEXT` | `VARCHAR(255)` / `TEXT` | Convert elastic TEXT fields to defined bounds where applicable. |
| `DECIMAL(12,2)` | `DECIMAL(12,2)` | Maintain precise monetary structures. |
| `TIMESTAMPTZ` | `TIMESTAMP` | Convert with default timezone offsets. |
| `DATE` | `DATE` | Identical format structures. |

### 1.1 Converted MySQL Tables DDL
```sql
-- Disable foreign keys check before run
SET FOREIGN_KEY_CHECKS = 0;

-- 1. Profiles Table
CREATE TABLE IF NOT EXISTS profiles (
  id VARCHAR(36) PRIMARY KEY,
  email VARCHAR(191) UNIQUE NOT NULL,
  name VARCHAR(255),
  phone VARCHAR(50),
  role VARCHAR(20) DEFAULT 'user' CHECK (role IN ('user', 'admin')),
  avatar_url VARCHAR(2048),
  currency VARCHAR(10) DEFAULT '₹',
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

-- 2. Categories Table
CREATE TABLE IF NOT EXISTS categories (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  user_id VARCHAR(36) NOT NULL,
  name VARCHAR(255) NOT NULL,
  type VARCHAR(50) NOT NULL CHECK (type IN ('income', 'expense', 'adjustment')),
  icon VARCHAR(100),
  color VARCHAR(50),
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (user_id) REFERENCES profiles(id) ON DELETE CASCADE
);

-- 3. Transactions Table
CREATE TABLE IF NOT EXISTS transactions (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  user_id VARCHAR(36) NOT NULL,
  category_id BIGINT,
  amount DECIMAL(12,2) NOT NULL,
  type VARCHAR(50) NOT NULL CHECK (type IN ('income', 'expense', 'adjustment')),
  description VARCHAR(500),
  date DATE NOT NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (user_id) REFERENCES profiles(id) ON DELETE CASCADE,
  FOREIGN KEY (category_id) REFERENCES categories(id) ON DELETE SET NULL
);

-- 4. Budgets Table
CREATE TABLE IF NOT EXISTS budgets (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  user_id VARCHAR(36) NOT NULL,
  category_id BIGINT NOT NULL,
  amount DECIMAL(12,2) NOT NULL,
  month VARCHAR(7) NOT NULL, -- Format: YYYY-MM
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY unique_user_cat_month (user_id, category_id, month),
  FOREIGN KEY (user_id) REFERENCES profiles(id) ON DELETE CASCADE,
  FOREIGN KEY (category_id) REFERENCES categories(id) ON DELETE CASCADE
);

SET FOREIGN_KEY_CHECKS = 1;
```

## 2. Authentication Replacement Strategy

Because Supabase Auth handles registrations, log-ins, and token handshakes automatically, migrating off Supabase requires implementing a native authentication engine in our central API.

Fortunately, our `package.json` already contains `bcryptjs` and `jsonwebtoken`. We will replace Supabase Auth with a custom local credential controller.

### 2.1 The New MySQL Authentication Flow
1.  **Register:** User submits an email, password, and profile data. The backend hashes the password using `bcryptjs` and inserts a new credentials record with a UUID into a custom table `users_credentials`.
2.  **Login:** The user submits their email and password. The backend queries `users_credentials` by email, verifies the password hash, and signs a custom JWT access token.
3.  **Validate:** Subsequent requests include the JWT in the `Authorization` Bearer header. The API verifies the signature and injects the payload user ID into query scopes.

## 3. Data Migration Execution Steps

```
+--------------------+      +--------------------+      +---------------------+
| Supabase Postgres  +----->+  Export CSV / JSON +----->+ Custom SQL Script   |
+--------------------+      +--------------------+      +----------+----------+
                                                                   |
                                                                   v
+--------------------+                                  +----------+----------+
| Remote MySQL DB    +<---------------------------------+ Load CSV/JSON Data  |
+--------------------+                                  +---------------------+
```

1.  **Stage 1: System Freeze:** Place the active application in temporary read-only maintenance mode.
2.  **Stage 2: Schema Provisioning:** Apply the new MySQL schema to the target remote MySQL instance.
3.  **Stage 3: Export Existing Records:** Export all tables from Supabase in CSV format.
4.  **Stage 4: Data Transformation:** Run a custom migration script to transform PostgreSQL schemas and formatting to clean MySQL types.
5.  **Stage 5: Import & Validate:** Load the converted records into the Remote MySQL database and run validation checks to ensure row counts and references match the original.

## 4. Key Migration Risks & Mitigation Guide

*   **Risk: Row Level Security Loss:** MySQL does not support out-of-the-box RLS policies like Postgres does.
    *   *Mitigation:* All queries inside `/api/index.ts` must explicitly filter on `user_id` inside core WHERE statements:
        `SELECT * FROM transactions WHERE user_id = ?;`
*   **Risk: Trigger Synchronization Delays:** PostgreSQL native functions like `handle_new_user` will cease executing.
    *   *Mitigation:* Enforce core transactional safety during user sign-up in code. Perform profile creation immediately after registering credentials within a single database transaction blocks.
